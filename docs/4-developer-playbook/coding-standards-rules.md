# มาตรฐานการเขียนโค้ดและกฎของโปรเจกต์

กฎในระบบนี้ไม่ได้มีไว้ขัดใจใคร แต่ละข้อมาจากบั๊กที่เคยเกิดขึ้นจริง
อ่านบทนี้แล้วจะรู้ว่าอะไรห้าม อะไรต้องทำ และไปเปิดไฟล์ไหนเมื่ออยากได้ถ้อยคำที่ผูกมัด

- 📚 **ไฟล์ต้นทางคือความจริง** — บทนี้สรุป ถ้าขัดกันให้ยึดไฟล์ต้นทาง
- 🧱 **แยกชั้นให้ชัด** — router ห้าม SQL, service ห้ามรู้จัก `Request`
- ✅ **ผ่านครบสี่คำสั่งก่อนคอมมิต** — `type-check` `lint` `test:unit` `build`

## ใครใช้บทนี้

บทนี้สำหรับนักพัฒนาทุกคนที่ส่งโค้ดเข้า repository นี้ และผู้ตรวจโค้ดที่ต้องตัดสินว่างานหนึ่งผ่านกฎหรือไม่

## กฎร่วมที่ห้ามละเมิด

- หน้าจอห้ามเชื่อมฐานข้อมูลโดยตรง ต้องเรียกผ่าน API ของ backend เท่านั้น
- ตัวตนผู้ใช้มาจาก token เท่านั้น ห้ามรับ `user_id` บทบาท หรือห้องจากสิ่งที่ผู้เรียกส่งมา
- ห้ามใช้ ORM ทั้งโปรเจกต์ ใช้ `asyncpg` และ SQL แบบมีพารามิเตอร์
- ห้ามฮาร์ดโค้ดความลับ ค่าทั้งหมดอ่านจาก `.env` ที่ root
- เวลาทั้งระบบยึด `Asia/Bangkok` และแสดงเป็นภาษาไทย
- ห้ามทำงานบน `main` ตรงๆ ให้สร้าง branch ตามประเภทงาน
- ภาษาของโค้ดและข้อความให้สอดคล้องกับไฟล์รอบข้าง ซึ่งในระบบนี้คือไทยเป็นหลัก

## กฎชั้น backend

### การแยกเลเยอร์

| ชั้น | ทำอะไร | ห้ามทำ |
|---|---|---|
| `routers/` | รับคำขอ ตรวจ dependency เรียก service แปลง exception | เขียน SQL หรือ business logic |
| `services/` | ตรวจสิทธิ์ เปิด transaction เขียน SQL เขียน audit | รู้จัก `Request` หรือสร้าง `HTTPException` |
| `models/` | นิยาม schema คำขอและคำตอบ | มี logic ที่แตะฐานข้อมูล |

router ดึงตัวตนด้วย `user_ctx: dict = Depends(get_current_user)` แล้วอ่าน `user_ctx.get("user_id")`
ห้ามอ่าน `x_user_id` หรือฟิลด์ใดใน body มาใช้เป็นตัวตน เพราะผู้เรียกปลอมได้
มีเทสต์คุมเรื่องนี้ใน `tests/test_home_summary.py`

### `response_model`

router ทุกตัวต้องประกาศ `response_model` เพื่อกรองฟิลด์ที่ไม่ควรออกไป
ข้อยกเว้นมีสามแบบ และต้องมีคอมเมนต์กำกับทุกครั้ง

1. **ดาวน์โหลดไฟล์** — `GET /api/import-student-template`
2. **SSE** — `GET /api/notifications/stream`
3. **ไม่มีเนื้อหา** — `204 No Content` ของ `DELETE /api/bookmarks/{id}`

ถ้าเพิ่ม endpoint ที่ไม่คืน JSON ก้อนเดียว ให้เขียนเหตุผลไว้ ไม่งั้นคนต่อไปจะคิดว่าลืม

### SQL

- ใช้ `$1, $2` ทุกครั้ง ห้ามต่อสตริง SQL
- mutation ที่แตะหลายตารางต้องอยู่ใน `async with conn.transaction():`
- PATCH ใช้ `req.model_dump(exclude_unset=True)` เพื่อไม่ให้ค่า `None` ทับของเดิม
- รายการยาวต้องมี `LIMIT` หรือใช้ `_envelope` ที่มี `count_params` และ `rows_params` แยกกัน
- เมื่อมีการอ่านแล้วเขียนที่แข่งกันได้ ต้องใช้ `SELECT ... FOR UPDATE` ใน transaction เดียวกัน
  และต้องมีเงื่อนไขสถานะอยู่ใน `WHERE` ด้วย ไม่ใช่ล็อกอย่างเดียว

::: tip รายการไฟล์ที่ใช้ `FOR UPDATE` เปลี่ยนได้ตามเวลา
อย่าคัดลอกจากเอกสาร ให้รัน `grep -rl "FOR UPDATE" backend/services/*.py` ใหม่ทุกครั้งที่ต้องอ้างถึง
:::

### การลบ

ค่าเริ่มต้นคือ soft delete ด้วย `UPDATE ... SET deleted_at = NOW()`
และทุกคำสั่งอ่านต้องมี `deleted_at IS NULL`

::: warning hard delete มีแค่สี่ตาราง
hard delete อนุญาตเฉพาะแถวชั่วคราวหรือ junction ที่ไม่ต้องเก็บประวัติ
ได้แก่ `push_subscriptions` `bookmarks` `push_outbox` และ `issue_countdowns`
ทุกคำสั่งต้องมีเงื่อนไขแคบและผูกกับเจ้าของ ไม่งั้นข้อมูลของคนอื่นหายถาวร
:::

ระบบนี้ไม่มีฟังก์ชันชื่อ `permanent` และไม่ต้องสร้างขึ้นมา

### Audit log

ทุกการกระทำที่เปลี่ยนข้อมูลต้องเรียก `AuditLogger("<ชื่อ service>").log(...)` ภายใน transaction เดียวกับข้อมูลหลัก
พร้อม `action` `actor_identifier` `client_source` `entity_type` `entity_id` `old_values` และ `new_values`

ฟิลด์บริบทที่ middleware เติมให้อัตโนมัติ ได้แก่ ip, user-agent, `trace_id`, endpoint และเวลาทำงาน
ห้าม router ประกอบบริบทเหล่านี้ส่งลงไปเอง
worker และสคริปต์ต้องครอบ `audit_scope()` เอง เพราะไม่มี HTTP middleware

ชื่อคลาสคือ `AuditLogger` ไม่ใช่ `service_logger`

### ข้อผิดพลาด

service โยน exception จาก `core.exceptions` และ router แปลงเป็น HTTP ตามรายการนี้

- 🚫 **`NotFoundError`** ➔ 404
- 🚫 **`ForbiddenError`** ➔ 403
- 🚫 **`ValidationError`** ➔ 400
- 🚫 **`ConflictError`** ➔ 409
- 🚫 **`ServiceUnavailableError`** ➔ 503

`ValidationError` ของ service คือ 400 แต่ของ Pydantic คือ 422 ซึ่ง FastAPI สร้างเอง
อย่าเขียน `except` สำหรับ 422 และอย่าถือว่าทั้งสองอย่างเป็นด่านเดียวกัน

ในระบบนี้ไม่มี `StudentNotFoundError` ชื่อนั้นมาจากโปรเจกต์เก่า

### รูปแบบโค้ด

- ตัวแปรและฟังก์ชันใช้ `snake_case` คลาสใช้ `PascalCase`
- ระบุ type hint ทั้งพารามิเตอร์และค่าที่คืน
- วันที่ใน schema ต้องเป็น `date` หรือ `datetime` ไม่ใช่ `str`
- Pydantic v2 ใช้ `model_dump()` ไม่ใช่ `dict()`

## กฎชั้นหน้าจอ

รายละเอียดภาพและองค์ประกอบอยู่ใน [มาตรฐาน UI/UX](ui-ux-design-standards.md)
กฎที่ต้องถือในระดับโค้ดมีดังนี้

- TypeScript เข้มงวด ห้าม `any`
- ห้ามเรียก `api.get` หรือ `api.post` จาก view ให้เพิ่มฟังก์ชันใน `services/`
- ชนิดข้อมูลอยู่ใน `types/` และต้องตรงกับ `response_model`
- ใช้ `src/services/api.ts` เป็น axios instance เดียว เพราะจัดการ token และ 401 ให้แล้ว
- ทุกการดึงข้อมูลต้องมี `const isLoading = ref(true)` และแสดง spinner หรือ skeleton
- การแจ้งผลต้องใช้ `Swal.fire` เท่านั้น
- เวลาและวันที่ต้องผ่าน `src/datetime.ts` ห้าม `toISOString()` เพื่อแสดงผล
- สีต้องมาจาก token ใน `tailwind.config.js` ห้ามค่า hex
- ห้ามนำ DaisyUI หรือ plugin ที่ใส่คลาสทั้งชุดกลับมา
- `<style>` ใช้เมื่อ Tailwind แสดงไม่ได้จริง และต้องมี `scoped`
- ชื่อไฟล์ component ใช้ `PascalCase` ตัวแปรใช้ `camelCase`

เงื่อนไขสถานะว่างต้องอิง `loading` และ `error` ไม่ใช่ความยาวของอาร์เรย์
และห้ามอ่านจากค่าที่มี `?? []` อยู่ต้นทาง

## กฎการเขียนเทสต์

รายละเอียดคำสั่งและสภาพแวดล้อมอยู่ใน [การทดสอบและการนำขึ้นระบบ](testing-and-deployment.md)
กฎที่ต้องถือมีดังนี้

- เทสต์เป็น integration กับ PostgreSQL จริง ไม่ใช่ mock
- แต่ละเทสต์เริ่มจากฐานข้อมูลว่าง เพราะ `clean_database` เป็น autouse
- ห้าม hardcode id ให้สร้างข้อมูลใน fixture แล้วคืนค่าออกมา
- ต้องตรวจฐานข้อมูลจริงหลังยืนยันสถานะ HTTP
- soft delete ให้ตรวจ `deleted_at IS NOT NULL` ไม่ใช่ตรวจว่าแถวหาย
- ห้าม mock `require_permission` ให้สร้างผู้ใช้ที่มีสิทธิ์จริง
- mock เฉพาะขอบที่ออกนอก process เช่นการยิงคิว หรือการส่ง push จริง
- ห้าม mock เวลา ให้ใช้ระยะห่างเป็นวันหรือชั่วโมงจากเวลาจริง
- เคสขอบเขตและ validation ใช้ `@pytest.mark.parametrize`
- แยกให้ออกว่า 400 มาจาก service และ 422 มาจาก schema
- เพิ่มตารางใหม่ต้องเพิ่มใน `_TABLES` ของ `conftest.py`
- เมื่อแก้บั๊กที่คนอื่นจะเจอซ้ำ ต้องบันทึกลง `docs/skills.md` ตามรูปแบบในไฟล์นั้น

## ขั้นตอนเมื่อต้องเพิ่ม endpoint

1. **เพิ่ม schema** คำขอและคำตอบใน `models/`
2. **เขียน service** ฟังก์ชันใน `services/` ที่รับ `pool` และ `user_id` ตรวจสิทธิ์ เปิด transaction เขียน SQL และเขียน audit
3. **ล็อกแถวถ้าจำเป็น** ใช้ `SELECT ... FOR UPDATE` เมื่อมีการอ่านแล้วเขียนที่แข่งกันได้
4. **เพิ่ม router** ฟังก์ชันใน `routers/` ที่ประกาศ `response_model` และแปลง exception
5. **เพิ่มฟังก์ชันเรียก API** ใน `frontend/src/services/`
6. **เพิ่มชนิดข้อมูล** ใน `frontend/src/types/`
7. **เขียนเทสต์** ที่ยืนยันสถานะ HTTP และตรวจฐานข้อมูล
8. **เพิ่มแถวใน [API Reference](api-reference.md)** ถ้าเป็น endpoint ที่คนอื่นต้องใช้

## ขั้นตอนเมื่อต้องเปลี่ยนโครงสร้างตาราง

1. **แก้ DDL** ใน `core/init_db.py`
2. **เขียน migration ใหม่** ใน `backend/migrations/` โดยไม่แก้ migration ที่รันแล้ว
3. **เพิ่ม index** ในบล็อก index ของ `init_db.py` ถ้าจำเป็น
4. **เพิ่มชื่อตาราง** ใน `_TABLES` ของ `conftest.py`
5. **ทดสอบทั้งสองกรณี** ฐานข้อมูลเปล่าและฐานข้อมูลที่มีข้อมูลเดิม
6. **อัปเดต [โครงสร้างฐานข้อมูล](database-schema.md)**

## ขั้นตอนเมื่อต้องเพิ่มสถานะ ตำแหน่ง หรือสิทธิ์

- สถานะของเรื่องต้องเพิ่มทั้งฝั่ง backend และป้ายใน `types/issue.ts` กับ `constants/status.ts`
- ตำแหน่งต้องเพิ่มใน `backend/config/roles.json` และป้ายใน `frontend/src/constants/roles.ts`
  ถ้าไม่เพิ่มป้าย หน้าจอจะแสดงรหัสภาษาอังกฤษ
- สิทธิ์ใหม่ต้องมีชื่อตัวพิมพ์ใหญ่ตรงกันทุกที่ เพราะการตรวจเป็นการเทียบสตริงตรง
- ตำแหน่งใหม่ต้องถูกพิจารณาใน `SCOPE_ALL_ROLES` `SCOPE_LEVEL_ROLES` และ `MANAGE_RANK`
  ถ้าไม่ระบุ ผู้ใช้จะเห็นน้อยลง ไม่ใช่เห็นมากขึ้น

## ระบบทำอะไรเบื้องหลัง

- `lint` รันทุกสคริปต์ที่ขึ้นต้นด้วย `lint:` ตามลำดับผ่าน `run-s` การเพิ่มด่านใหม่ทำได้ด้วยการเพิ่มสคริปต์
- `lint:colors` ปฏิเสธค่า hex ของสีแบรนด์ในเทมเพลต
- `lint:palette` ปฏิเสธสีเขียวชุดอื่นเพื่อบังคับให้ใช้ `ok-*`
- `api.ts` แนบ token และพาไปหน้าเข้าสู่ระบบเมื่อได้ 401
- `api.ts` แปลงรายการ 422 เป็นข้อความไทยที่ผู้ใช้อ่านได้
- middleware ตั้ง `trace_id` ทุกคำขอและใส่ `X-Trace-Id` ในคำตอบ

## ข้อจำกัดและข้อควรระวัง

- ไม่มี lint หรือ type check สำหรับ Python ความถูกต้องจึงพึ่งเทสต์เป็นหลัก
- ไม่มี CI บน GitHub ด่านทั้งหมดรันบนเครื่องก่อน push
- `lint:palette` ยังไม่ครอบ `amber` และ `red` จึงต้องตรวจด้วยตา
- กฎที่เขียนในหลายไฟล์จะเลื่อนออกจากกันได้ ให้ยึดไฟล์ต้นทางและแก้บทนี้เมื่อพบความต่าง
- ตัวเลขที่วัดได้ เช่นจำนวน endpoint หรือจำนวนไฟล์ ให้ระบุวันที่วัดหรือไม่ต้องระบุเลย

## ติดปัญหาตรงไหน? ดูวิธีแก้ตรงนี้เลย

**Q: router ต้องสร้าง audit context เองไหม?**

👉 **วิธีแก้:** ไม่ต้อง middleware ตั้งให้แล้ว
router ส่งเพียง `actor_identifier` `client_source` และรายละเอียดการกระทำ
ส่วน ip และ `trace_id` ถูกเติมอัตโนมัติ

**Q: service โยน `ValidationError` แล้วได้ 400 แต่บางที่ได้ 422?**

👉 **วิธีแก้:** สองตัวนี้คนละชั้น
`core.exceptions.ValidationError` คือ 400 จาก business rule
ส่วน 422 มาจาก Pydantic ตอน schema ไม่ผ่าน และ FastAPI สร้างให้ก่อนถึง service

**Q: ลบข้อมูลแล้วต้องใช้ `DELETE FROM` ได้ไหม?**

👉 **วิธีแก้:** ได้เฉพาะตารางที่ระบุไว้ในรายการ hard delete
นอกนั้นให้ตั้ง `deleted_at` และตรวจว่าทุกคำสั่งอ่านมีเงื่อนไข `deleted_at IS NULL`

**Q: เขียน `<style>` ใน component ได้ไหม?**

👉 **วิธีแก้:** ได้เมื่อ Tailwind ทำไม่ได้จริง เช่น keyframes หรือ `::v-deep`
ต้องมี `scoped` และไม่ควรใช้เป็นที่ทิ้งสไตล์ที่เขียนเป็น utility class ได้

**Q: เพิ่มสีใหม่ในหน้าจอทำอย่างไร?**

👉 **วิธีแก้:** เพิ่ม token ใน `tailwind.config.js` พร้อมเหตุผล แล้วใช้ชื่อ token
ห้ามพิมพ์ค่า hex ในเทมเพลต เพราะ `lint:colors` จะปฏิเสธ และค่าจะเลื่อนออกจากกันเมื่อมีคนแก้ที่เดียว

**Q: เทสต์ต้องสร้างห้องและผู้ใช้เองทุกครั้งหรือไม่?**

👉 **วิธีแก้:** ใช่ เพราะฐานข้อมูลถูกล้างก่อนทุกเทสต์
ให้สร้างใน fixture และคืน id กับ token ออกมา ห้ามอ้าง `room_id = 1`

**Q: ต้องเขียน `docs/skills.md` ทุกครั้งที่แก้บั๊กไหม?**

👉 **วิธีแก้:** เขียนเมื่อเป็นบทเรียนที่คนอื่นจะเจอซ้ำ
ก่อนเขียนให้ค้นหัวข้อเดิมก่อน ถ้ามีหัวข้อใกล้เคียงอยู่แล้วให้แก้รายการนั้น ไม่ใช่เพิ่มรายการที่ขัดกัน

**Q: งานที่แตะทั้ง backend และหน้าจอ ต้องทำอย่างไร?**

👉 **วิธีแก้:** ทำ backend ให้เสร็จและเทสต์ผ่านก่อน แล้วจึงต่อหน้าจอ
ตรวจว่า `response_model` กับชนิดฝั่งหน้าจอตรงกัน และอัปเดต [API Reference](api-reference.md) ในรอบเดียวกัน
