# มาตรฐาน UI/UX

หน้าจอทุกหน้าใน PIRIvoice ต้องดูเป็นชิ้นเดียวกัน ไม่ใช่ชุดหน้าที่ทำโดยคนละคน
บทนี้คือภาษากลางที่ทุกคนใช้ร่วมกัน เปิดคู่กับโค้ดตอนลงมือได้เลย

- 🎨 สี มุมโค้ง และตัวอักษรมาจาก token เท่านั้น
- 🧩 ถ้าองค์ประกอบกลางทำได้ อย่าสร้างปุ่มหรือการ์ดใหม่
- 🚦 ทุกหน้ามีสามสถานะ กำลังโหลด ว่าง และผิดพลาด ห้ามปนกัน

## ใครใช้บทนี้

นักพัฒนาหน้าบ้านที่ต้องสร้างหรือแก้ view และ component
รวมถึงผู้ออกแบบที่ต้องรู้ว่าอะไรถูกกำหนดไว้แล้วและอะไรยังเลือกได้

## ก่อนเริ่ม

- เปิด `frontend/tailwind.config.js` และ `frontend/src/components/ui/` ประกอบ
- เปิด `docs/rules/frontend.md` §4 และ §6 ซึ่งเป็นกฎที่บังคับใช้
- เข้าใจว่าระบบมีภาษาเดียวคือไทย และมีธีมเดียวคือสว่าง

## ทิศทางภาพ

ระบบใช้แนว Editorial & Civic คืออ่านง่าย เป็นทางการ และไม่ตกแต่งเกินจำเป็น
ลำดับชั้นของข้อมูลเกิดจากช่องว่าง เส้น 1 พิกเซล และน้ำหนักตัวอักษร ไม่ใช่จากเงา

- 🧱 **การ์ด** — พื้นขาว เส้นขอบ 1px มุม 16px ไม่มีเงา
- 🌫️ **เงา** — ใช้ได้เฉพาะ `fab` และ `sheet` ที่นิยามใน config
- 🎨 **สี** — มาจาก token เท่านั้น ห้ามพิมพ์ค่า hex ในเทมเพลต
- 🔴 **สีแบรนด์** — ใช้กับปุ่มหลักและสิ่งที่ต้องสนใจ ไม่ใช้เป็นสีตกแต่ง
- 🏷️ **สถานะ** — สีสื่อความหมายได้ แต่ต้องมีข้อความกำกับเสมอ

## องค์ประกอบกลาง

ห้ามสร้างปุ่มหรือการ์ดใหม่ด้วย utility class ถ้าองค์ประกอบกลางทำได้
ถ้าต้องการลักษณะใหม่ ให้เพิ่ม variant ที่องค์ประกอบกลาง ไม่ใช่คัดลอกไปไว้ในหน้า

| องค์ประกอบ | ใช้เมื่อ | ตัวเลือกสำคัญ |
|---|---|---|
| `AppCard` | กลุ่มเนื้อหาที่เป็นหน่วยเดียว | `padded` `interactive` `muted` |
| `AppButton` | การกระทำทุกชนิด | `variant` `size` `loading` `block` `to` |
| `AppChip` | ตัวกรองหรือป้ายสั้น | ใช้คู่กับ `AppTabs` |
| `AppTabs` | สลับมุมมองในหน้าเดียว | `key` `label` `badge` |
| `AppSheet` | ตัวเลือกชั่วคราวจากด้านล่าง | ใช้กับการเลือกที่ยาว |
| `AppEmptyState` | ทั้งหน้าว่าง | `icon` `title` `description` `compact` |
| `AppEmptyRow` | บล็อกย่อยที่ว่าง | `tone` เป็น `ok` หรือ `neutral` |
| `IconButton` | การกระทำที่ไม่ต้องมีข้อความ | ต้องมี `aria-label` เสมอ |
| `PageHeader` | หัวหน้าและปุ่มหลักของหน้า | ใช้หนึ่งครั้งต่อหน้า |
| `StatusBadge` | แสดงสถานะเรื่อง | `label` `size` `hideDot` |

`AppButton` มี variants `primary` `secondary` `text` `danger` และ `light`
ขนาด `sm` สูง 36px แต่ถ่างพื้นที่กดเป็น 44px ด้วย `after:` จึงใช้ใน toolbar ได้

`StatusBadge` แสดงจุดสีนำหน้าข้อความเสมอ เพราะสีอย่างเดียวอ่านไม่ได้สำหรับผู้ใช้ที่ตาบอดสี
และหายไปเมื่อพิมพ์ขาวดำ ถ้าบริบทบอกสถานะซ้ำอยู่แล้วจึงใช้ `hideDot`

`AppEmptyRow` ใช้เมื่อบล็อกหนึ่งว่างเป็นเรื่องปกติ เช่น "ไม่มีเรื่องค้าง"
ส่วน `AppEmptyState` ใช้เมื่อทั้งหน้าไม่มีข้อมูลและผู้ใช้ควรมีทางออก

## โครงหน้า

`MainLayout` เป็น layout เดียวของแอป ประกอบจาก shell เหล่านี้

- `AppHeader` แถบหัวด้านบน
- `AppSidebar` เมนูด้านข้างบนจอใหญ่
- `AppBottomNav` แท็บล่างห้าช่องบนจอเล็ก
- `AppTabBar` แท็บย่อยในหน้า
- `AppFab` ปุ่มลอยสำหรับการกระทำหลัก
- `AppNavRow` และ `AppGroupHeader` สำหรับหน้าถัดไป

แท็บล่างห้าช่องมีป้ายคือ **หน้าแรก** **เรื่อง** **บอร์ด** **กิจกรรม** และ **เพิ่มเติม**
ลำดับและป้ายนิยามใน `constants/nav.ts` ที่เดียว

เมนูที่ต้องมีสิทธิ์จะไม่แสดงถ้าผู้ใช้ไม่มีสิทธิ์
นอกจากนี้ยังมีธง `councilOnly` สำหรับเมนูของสภา และ `hiddenFromMenu` สำหรับหน้าที่เข้าทางอื่น
อย่าเขียนเงื่อนไขสิทธิ์ซ้ำในเทมเพลต ให้ใช้ธงใน `nav.ts`

## สถานะของหน้าจอ

สถานะสามอย่างนี้ต้องแยกออกจากกันเด็ดขาด

| สถานะ | ผู้ใช้เห็น | เงื่อนไข |
|---|---|---|
| กำลังโหลด | skeleton หรือ spinner | `loading` เป็นจริง |
| ว่าง | ข้อความว่าว่างเพราะอะไรและทำอะไรต่อได้ | `!loading && !error` และรายการว่าง |
| ผิดพลาด | ข้อความผิดพลาดและปุ่มลองใหม่ | `error` เป็นจริง |

ห้ามตัดสินว่าว่างจาก `list.length === 0` เพียงอย่างเดียว
เงื่อนไขสถานะควรเป็นฟังก์ชันบริสุทธิ์ที่ทดสอบได้ เช่นเดียวกับ `pendingOnMeBlockState()` ใน `types/home.ts`
ค่าที่ยังไม่รู้ต้องถือว่าไม่ว่าง เพื่อไม่ให้ประกาศผลผิด

::: warning ว่างไม่ใช่ศูนย์ และล่มก็ไม่ใช่ว่าง
อย่าอ่านจากตัวแปรที่มี `?? []` อยู่ต้นทาง เพราะตอนผิดพลาดค่านั้นกลายเป็นอาร์เรย์ว่าง
แล้วหน้าจอจะบอกผู้ใช้ว่าไม่มีงานค้าง ทั้งที่ระบบล่ม — ผู้ใช้จะเลิกตามงานไปเลย
:::

## การแจ้งผลและการยืนยัน

- ใช้ `Swal.fire` จาก SweetAlert2 เท่านั้น ห้ามใช้ `alert()` หรือ toast อื่น
- สีปุ่มใน dialog ต้องมาจาก `constants/brand.ts` ไม่ใช่ค่าคงที่ในไฟล์
- การลบหรือการกระทำที่ย้อนกลับไม่ได้ต้องมีการยืนยัน และบอกผลที่จะเกิดขึ้น
- ข้อความสำเร็จต้องบอกสิ่งที่เกิดขึ้นจริง เช่น "ย้ายนักเรียน 32 คนแล้ว"
- การกระทำที่ใช้เวลานานต้องแสดง `loading` บนปุ่มและกันการกดซ้ำ

## เวลาและวันที่

ทุกฟังก์ชันใน `src/datetime.ts` ตรึงเขตเวลา `Asia/Bangkok` และใช้ปีพุทธศักราช
ห้ามใช้ `toISOString()` เพื่อแสดงผล เพราะคืนเวลา UTC และปี ค.ศ.

- 📅 `fmtDateTime` — วันและเวลาปกติ
- 🕐 `fmtTime` — เวลาอย่างเดียว
- 📆 `fmtDayTime` — วันแบบสั้นและเวลา
- ⏱️ `fmtDateTimeSec` — เวลาที่ต้องละเอียดถึงวินาที
- 🗓️ `fmtDateShort` — วันที่แบบสั้นในแถวรายการ
- ⏳ `fmtRelative` — "5 นาทีที่แล้ว"
- 📚 `fmtDayGroup` — หัวกลุ่มรายวันในรายการแจ้งเตือน

ช่องกรอกวันที่แบบ `datetime-local` ส่งสตริงที่ไม่มีเขตเวลา ใช้ `toLocalInput` `inputToDate` และ `dateToInput`
ในการแปลง และให้ backend เติมเขตเวลาให้

## การเข้าถึง

- พื้นที่กดขั้นต่ำ 44dp ทั้งด้านกว้างและด้านสูง
- ใช้ `:focus-visible` ไม่ใช่ `:focus` เพื่อไม่ให้ผู้ใช้เมาส์เห็นริงโดยไม่จำเป็น
- ปุ่มที่กำลังโหลดต้องมี `aria-busy` และปุ่มที่ปิดต้องมี `aria-disabled`
- ไอคอนที่ไม่มีข้อความต้องมี `aria-label` และไอคอนที่ตกแต่งต้องมี `aria-hidden`
- ภาษาไทยต้องการระยะบรรทัดมากกว่าภาษาอังกฤษ ใช้ค่าจาก token ไม่ใช่กำหนดเอง
- แถบที่ติดขอบล่างต้องเผื่อ `env(safe-area-inset-bottom)` เพื่อไม่ทับแถบ gesture ของ iPhone
- ข้อความสถานะต้องอ่านออกโดยไม่เห็นสี

## การรองรับหน้าจอ

- ออกแบบจากจอ 390×844 ก่อน แล้วขยายขึ้นไปที่ 768 และ 1280
- ตารางที่กว้างให้เลื่อนในกรอบของตัวเอง ห้ามให้ทั้งหน้าเลื่อนแนวนอน
- หน้าจัดการใช้ความกว้าง 1280 เป็นหลัก และต้องไม่พังที่ 1024
- อย่าใช้ตัวเลขขนาดตายตัวที่ขึ้นกับความกว้างจอ ให้ใช้ flex และ grid

## ขั้นตอนสร้างหน้าจอใหม่

1. **เพิ่ม route และเมนู** ถ้ายังไม่มี ให้แก้ `router/index.ts` และ `constants/nav.ts`
2. **เพิ่มฟังก์ชันเรียก API ใน `services/`** อย่าเรียก `api.get` จาก view
3. **เพิ่มชนิดข้อมูลใน `types/`** ให้ตรงกับ `response_model`
4. **ประกอบหน้าจาก `PageHeader` การ์ด และองค์ประกอบกลาง** ไม่สร้างของใหม่
5. **ทำครบสามสถานะ** คือ loading ว่าง และผิดพลาด โดยแยกเงื่อนไขให้ชัด
6. **ใช้ `AppButton` กับทุกการกระทำ** และใช้ `Swal.fire` กับผลลัพธ์
7. **แสดงเวลาและวันที่ผ่าน `datetime.ts` เท่านั้น**
8. **ตรวจว่าปุ่มทุกปุ่มกดได้ด้วยคีย์บอร์ด** และมีพื้นที่กด 44dp
9. **เพิ่มภาพหน้าจอในคู่มือ** ถ้าผู้ใช้เห็นหน้าใหม่

## ระบบทำอะไรเบื้องหลัง

- `lint:colors` ปฏิเสธการใช้ `[#B91C1C]` และ `[#991B1B]` ในเทมเพลต
- `lint:palette` ปฏิเสธ `emerald` `green` `teal` และ `lime-<ตัวเลข>` ให้ใช้ `ok-*` แทน
- สคริปต์ `lint` รันทุก `lint:*` ตามลำดับผ่าน `run-s`
- `services/api.ts` แนบ token และแปลง 401 เป็นการพาไปหน้าเข้าสู่ระบบ
- `services/api.ts` แปลงรายการ 422 ของ Pydantic เป็นข้อความไทยที่อ่านได้
- `stores/notifications.ts` poll badge ทุก 30 วินาทีและหยุดเมื่อล้มติดกันสามครั้ง
- `MainLayout` คำนวณเมนูตามสิทธิ์และขนาดจอตอนโหลดหน้า

::: tip เพิ่มด่านตรวจใหม่ได้ด้วยสคริปต์เดียว
การเพิ่มด่านใหม่ทำได้ด้วยการเพิ่มสคริปต์ `lint:xxx` แล้ว `run-s` จะเก็บไปรันให้เอง
ไม่ต้องแก้รายการคำสั่งที่ไหนอีก
:::

## ข้อจำกัดและข้อควรระวัง

- ระบบมีเฉพาะภาษาไทย ไม่มีตัวเลือกภาษา
- ระบบมีเฉพาะธีมสว่าง ไม่มีโหมดมืด
- ยังไม่ครอบสี `amber` และ `red` ด้วย `lint:palette` จึงเป็นหนี้ที่ต้องตรวจด้วยตา
- ห้ามนำ DaisyUI หรือ plugin ที่ใส่คลาสทั้งชุดกลับมา
- `AppButton` ขนาด `sm` ต่ำกว่า 44dp โดยตัวปุ่ม แต่ถ่างพื้นที่กดด้วย pseudo-element ถ้าลบคลาสนั้นจะผิดเกณฑ์
- เงาใหม่ต้องเพิ่มใน config พร้อมเหตุผล ไม่ใช่พิมพ์ arbitrary value ในเทมเพลต

::: warning อย่ารัน npm run format ทั้ง repo นะ
มันจะจัดรูปแบบไฟล์ที่ไม่ได้แตะ และลอก `;` จาก inline handler ทำให้ build แตกได้
format เฉพาะไฟล์ที่แก้เท่านั้น

## ติดปัญหาตรงไหน? ดูวิธีแก้ตรงนี้เลย

**Q: ต้องการปุ่มสีแดงแบบใหม่ ควรเขียนเองหรือเพิ่ม variant?**

👉 **วิธีแก้:** เพิ่ม variant ใน `AppButton` เพราะปุ่มที่เขียนเองทำให้ระบบมีสีและขนาดปนกัน ถ้าเป็นปุ่มอันตรายให้ใช้ `danger` ซึ่งเป็นข้อความแดงไม่มีขอบแดง เพื่อไม่ให้ปุ่มอันตรายกลายเป็นเรื่องปกติ

**Q: หน้าจอขึ้น "ไม่มีข้อมูล" ทั้งที่เซิร์ฟเวอร์ล่ม?**

👉 **วิธีแก้:** เงื่อนไขว่างอ่านค่าที่ผ่าน `?? []` อยู่ต้นทาง ให้แยกตัวแปร `loading` `error` และรายการออกจากกัน และให้เงื่อนไขว่างต้องมี `!loading && !error`

**Q: จะใช้ `emerald` ในหน้าจอใหม่ได้ไหม?**

👉 **วิธีแก้:** ไม่ได้ `lint:palette` จะปฏิเสธ ให้ใช้ `ok-tint` `ok-strong` `ok-bright` หรือ `ok-solid` ตามความหมาย ไม่ใช่ตามเฉดที่ชอบ

**Q: ต้องแสดงสถานะด้วยสีอย่างเดียวได้ไหม?**

👉 **วิธีแก้:** ไม่ควร และในระบบนี้ไม่ควรทำเดี่ยว ๆ ให้ใช้ `StatusBadge` ซึ่งมีทั้งจุดสีและข้อความ และถ้าซ่อนจุดต้องมีบริบทที่บอกสถานะซ้ำแล้วจริง

**Q: ต้องการเงาให้การ์ดเด่นขึ้น ทำได้ไหม?**

👉 **วิธีแก้:** ไม่ได้ เพราะการ์ดในระบบนี้ไม่มีเงา ให้ใช้การ์ด `interactive` ที่เปลี่ยนเส้นขอบเมื่อ hover หรือเพิ่มระยะห่างและหัวข้อแทน

**Q: แสดงวันที่แล้วได้ปี ค.ศ. หรือเวลาผิด?**

👉 **วิธีแก้:** มักเกิดจากการใช้ `toISOString()` หรือสร้าง `Intl` เองโดยไม่ระบุเขตเวลา ให้ใช้ฟังก์ชันใน `datetime.ts` ซึ่งตรึง `Asia/Bangkok` และปีพุทธศักราชแล้ว

**Q: ข้อความยาวในการ์ดถูกตัดบนจอเล็ก?**

👉 **วิธีแก้:** อย่าตั้งความสูงคงที่กับการ์ดที่มีข้อความ ให้ปล่อยให้ความสูงตามเนื้อหา และจำกัดความกว้างของข้อความด้วย `max-w-*` ที่เหมาะกับบริบท

**Q: เพิ่มเมนูใหม่แล้วคนที่ไม่มีสิทธิ์ยังเห็น?**

👉 **วิธีแก้:** อย่าเขียนเงื่อนไขในเทมเพลต ให้ใส่ `permission` หรือ `councilOnly` ใน `constants/nav.ts` และตรวจว่า route มี guard ฝั่ง router ด้วย เพราะการซ่อนเมนูไม่ใช่การป้องกัน
